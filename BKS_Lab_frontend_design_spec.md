# BKS Lab --- техническое дизайн-ТЗ для frontend

**Версия:** 1.1\
**Стек:** React + JavaScript\
**Цель:** реализовать главную и блог BKS Lab по фирменным референсам с
преимущественно светлой основой и локальными navy/cyan-акцентами.
Обязательный приоритет --- WCAG 2.2 AA, клавиатурная навигация и
корректная работа NVDA, JAWS, VoiceOver и TalkBack.

**Уточнение владельца от 08.10.2026:** предпочтение светлым фонам,
сочетание светлых и тёмных элементов уточняется в процессе работы.
Первый рабочий вариант: светлые header, контент и footer; фотография с
объёмным логотипом и финальный statement — тёмные. Основа композиции —
`референсы/Лаборатория технологий BKS Lab.png` и
`референсы/BKS lab_ технологии для людей.png`. Структура секций, название,
знак «лупа + </>», основные CTA и требования доступности сохраняются.

## 1. Концепция

BKS Lab --- персональная технологическая площадка: проекты, современная
разработка, архитектура, управление IT-проектами, AI, доступность и
авторские материалы.

Визуальный язык: технологическая лаборатория + IDE + современный
editorial-сайт. Не делать «хакерский терминал». Интерфейс спокойный,
контрастный, с большим количеством воздуха.

Фирменные фразы: `IDEAS / CODE / PEOPLE`;
`TECHNOLOGY FOR A MORE OPEN WORLD`; «Разработка. Управление.
Искусственный интеллект. Идеи, которые работают.»

## 2. Технологическая база

Использовать React, JavaScript, семантический HTML5. Роутинг --- React
Router, если SPA. Стили --- CSS Modules либо принятая CSS-система.
Дизайн-токены вынести в CSS custom properties. Архитектура должна
позволять позднее подключить CMS/API.

``` text
src/
  assets/
  components/{layout,navigation,projects,blog,ui}/
  pages/{HomePage,BlogPage,ArticlePage,ProjectsPage,ProjectPage,AboutPage,ContactsPage}/
  data/
  styles/{tokens.css,global.css}
  App.jsx
public/{brand,images,og}/
```

Не создавать монолитные компоненты страниц.

## 13. Light theme

Светлая тема — базовая палитра, тёмная включается системной настройкой
или ручным выбором. Переключатель --- `<button>` с
понятным accessible name, например `Переключить на светлую тему`.
Учитывать `prefers-color-scheme`, но ручной выбор пользователя имеет
приоритет и сохраняется в localStorage. DOM-порядок между темами не
менять.

Инициализация в `<head>` выполняется до первого paint. Изменение системной
темы учитывается только до ручного выбора; выбор синхронизируется между
вкладками. При запрете localStorage переключатель продолжает работать
в текущем документе. Без JavaScript остаётся читаемая светлая версия.

## 14. Accessibility --- обязательно

Цель: **WCAG 2.2 AA**.

### Семантика

Использовать `header`, `nav`, `main`, `section`, `article`, `aside`,
`footer`. Один `<main>` и один H1 на страницу. Иерархия заголовков
логичная.

В начале документа:

``` html
<a class="skip-link" href="#main-content">Перейти к основному содержимому</a>
```

Основная область: `<main id="main-content" tabindex="-1">`.

### Клавиатура и focus

Всё интерактивное доступно Tab/Shift+Tab. Использовать нативные
button/link/input. Не использовать положительный `tabindex`. Порядок
фокуса совпадает с DOM и визуальным порядком.

`focus-visible` --- заметный outline минимум 2--3 px + offset. Никогда
не убирать outline без равноценной замены.

### Screen readers

Не добавлять ARIA там, где есть нативный HTML. Декоративные иконки
внутри подписанных кнопок --- `aria-hidden="true"`. Icon-only button
обязательно получает `aria-label`. Динамические сообщения использовать
умеренно; большие области не делать `aria-live`.

### Контраст и масштаб

Обычный текст минимум 4.5:1, крупный минимум 3:1, UI/focus минимум 3:1.
Проверить фактические пары автоматически и вручную. Интерфейс обязан
работать при browser zoom 200%, text zoom и reflow на 320 CSS px. Не
запрещать zoom в viewport.

### Motion

Соблюдать `prefers-reduced-motion: reduce`: отключать декоративные
transitions, animations и parallax. Glow не должен мигать/пульсировать.

### Touch

Цели на мобильных --- ориентир минимум 44×44 CSS px и достаточное
расстояние между элементами.

### Формы

Каждое поле имеет label. Required сообщается текстом и программно.
Ошибка содержит текст, а не только красную рамку. После ошибки фокус
перемещается предсказуемо на summary или первое ошибочное поле.

## 17. Состояния UI

Для интерактивных компонентов реализовать default, hover, focus-visible,
active и, где применимо, disabled/loading/error/success. Hover не должен
быть единственным способом получить важную информацию. Skeleton ---
декоративный, скрывается от screen reader через `aria-hidden="true"`.

## 18. Иконки

Использовать единый SVG-набор: поиск, тема, меню, закрыть, стрелка,
разработка, управление, AI, люди/доступность. Декоративные SVG:
`aria-hidden="true" focusable="false"`. Самостоятельная icon-button
имеет accessible name. Emoji не использовать как основные UI-иконки.

## 19. Визуальное соответствие утверждённому макету

Сохранить: - светлую основу и локальные глубокие navy-блоки (в тёмной теме
navy становится основным фоном); - cyan линии и акценты; - холодные
тонкие границы; - карточки почти без тяжёлых теней; - крупный 3D BKS Lab
знак в hero; - бетонную/архитектурную фактуру только как локальный
hero-образ; - контрастные крупные заголовки; - моноширинные мелкие
технические подписи; - небольшие cyan glow-эффекты; - аккуратные
pill-теги; - ощущение профессионального engineering/editorial продукта.

Не превращать каждую секцию в стеклянную карточку. Не злоупотреблять
blur, glow, gradients и 3D. Основной контент должен быть максимально
читаемым.

## 20. Производительность

Цели: Lighthouse Performance и Accessibility без очевидных регрессий.
Минимизировать layout shift; задавать `width`/`height` или
`aspect-ratio` изображениям; code-split тяжёлые страницы при
необходимости; не грузить icon library целиком ради нескольких иконок;
избегать тяжёлого JS для визуальных эффектов; шрифты грузить экономно.

## 21. Поведение роутинга

При клиентской навигации: - обновлять `document.title`; - после перехода
корректно переводить контекст пользователя к началу нового main/H1, не
оставляя screen reader «в старой странице»; - сохранять стандартное
поведение Back/Forward; - deep links должны открываться напрямую; - URL
категорий/статей должен быть осмысленным.

## 22. Проверка доступности перед сдачей

Обязательно выполнить: 1. Полный проход только клавиатурой. 2. NVDA +
Chrome/Firefox на Windows: header, меню, hero, карточки, blog filters,
search, формы. 3. Проверить хотя бы базовый сценарий VoiceOver/Safari
или TalkBack/Chrome. 4. axe/Lighthouse accessibility audit. 5. Проверка
контраста. 6. Zoom 200%. 7. Reflow около 320 CSS px. 8.
`prefers-reduced-motion`. 9. High Contrast/forced-colors --- основные
действия должны оставаться различимыми. 10. Отключить CSS/изображения и
убедиться, что структура и смысл страницы сохраняются.

## 23. Definition of Done

Работа считается завершённой, когда: - `/` и `/blog` визуально
соответствуют макету и этому документу; - responsive работает от
мобильного до широкого desktop; - все указанные asset slots
предусмотрены; - logo/favicon/OG структура подготовлена; - навигация
полностью работает с клавиатуры; - страницы логично читаются NVDA; - нет
кликабельных `div/span`; - focus хорошо виден; - контраст соответствует
AA; - изображения имеют корректные alt/пустой alt; - заголовки и
landmarks семантически корректны; - фильтры и поиск доступны; - тема не
ломает контраст; - нет критических axe-ошибок; - контент не зависит от
hover, цвета или изображения; - код разбит на переиспользуемые
компоненты.

## 24. Что не придумывать агенту самостоятельно

Без отдельного согласования не менять: - основной знак «лупа + `</>`»; -
название `BKS Lab`; - основную navy/cyan палитру; - структуру главной; -
структуру блога; - принцип 3D-логотипа в hero; - требования WCAG 2.2
AA; - тексты основных CTA и названия разделов.

Если финальных SVG/фото ещё нет, использовать временные placeholders с
теми же именами файлов и размерами. Не генерировать случайные «похожие»
логотипы внутри frontend-кода.

## 25. Приоритеты реализации

**P0:** семантика, доступность, responsive, header/navigation, главная,
блог, палитра, typography, asset API.\
**P1:** light theme, поиск/фильтры, формы подписки, SEO/OG, polish.\
**P2:** дополнительные micro-interactions и декоративные эффекты.

При конфликте визуального эффекта с доступностью, читаемостью или
производительностью приоритет всегда у доступности, содержания и
предсказуемого поведения интерфейса.
