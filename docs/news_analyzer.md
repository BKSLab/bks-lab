# News Analyzer — интеграция и эксплуатация

## Автоматические «Заметки на полях»

Страница `/admin/news/notes` управляет отдельной очередью коротких заметок.
Включение режима фиксирует начальный момент: только впервые найденные
после него материалы могут попасть в автоматическую очередь. Повторное
включение после паузы не сбрасывает этот момент. Ранее собранная история
задним числом не публикуется.

Один запрос LLM возвращает редакционный анализ и заготовку заметки:
заголовок до 90 символов и текст до 300 символов с пробелами. Ссылка и
название источника задаются сервером. В очередь проходят релевантные
материалы без дубля и признака необходимости проверки, с достаточным
исходным текстом. Это автоматический отбор, а не независимая проверка фактов.

Подготовленная запись хранится черновиком в общем контенте с ревизией.
Очередь имеет состояния `queued`, `published`, `excluded`, `expired`;
обычные ручные черновики воркер не затрагивает. В админке можно изменить
текст и заголовок кандидата, исключить запись и настроить темп публикаций.
Повторный анализ не создаёт вторую заметку и не перезаписывает редакторские правки.

Публикатор работает в существующем `news-analyzer-scheduler` независимо
от доступности LLM: готовой записи повторный вызов модели не нужен.
Публикуется не более одной записи за интервал (по умолчанию 10 минут,
настраивается). Последнее время публикации хранится в БД; рестарты и
пропущенные интервалы не создают пачки публикаций. Срок актуальности по
умолчанию 72 часа; просроченная запись получает объяснение в очереди.
Черновик, очередь, ревизия и время публикации изменяются атомарно;
frontend-кеш обновляется после commit. Очистка сырой истории сохраняет
опубликованные заметки, происхождение и защиту от повторной публикации.

На главной находится компактная прокручиваемая лента, `/notes` содержит
полный архив. Модельный текст выводится как обычный текст, подпись
«Подробнее…» ведёт на первоисточник. Ручной Markdown и связанные статьи
поддерживаются. Новые записи показываются по кнопке уведомления, без
скачков читаемого списка. Курсорная подгрузка использует точное время
публикации и стабильный порядок; первая порция и ссылки архива доступны
в серверном HTML для индексации и работы без JavaScript.

Миграция `0011` расширяет хранилище без сброса данных. Начальное состояние
новой функции выключено; включение выполняется через защищённый API/админку.
Для данного выпуска владелец поручил включить режим после проверки выкладки.

Основание: `search_news/BKS_Lab_News_Analyzer_TZ.md` и каталог источников
`search_news/BKS_Lab_AI_Sources_Research.md`. Реализация MVP: RSS/Atom и HTML,
внешняя LLM, редакционные решения. Найденные материалы не публикуются
автоматически и не изменяют Markdown сайта.

## Проверенный каталог и добавление источника

Каталог админки определяется `backend/src/news_sources/registry.py`.
Каждый источник имеет отдельный модуль `SourceProfile`: адрес ленты/списка,
правила публикаций и текста, краткое описание и рекомендуемый календарь.
Общая инфраструктура RSS/HTML, безопасный HTTP и очистка текста используются
совместно. Эти технические параметры не редактируются пользователем.

Для добавления сайта:

1. Создать модуль профиля с постоянными `id`/`slug`, точными правилами
   списка/статьи и подходящим `default_schedule`; добавить его в реестр.
2. Выполнить безопасную проверку списка, текста и повторного сбора:

   ```bash
   python -m scripts.audit_news_catalogue --profiles --only profile-id --output /tmp/source-audit.json --collect --repeat-collect
   ```

3. Проверить результаты обоих проходов, canonical URL и хеши. Для проверки
   HTML статьи независимо от полного текста RSS добавить `--verify-articles`;
   для обычного начального окна — `--lookback-days 30`. Пустое окно старого
   блога не равно ошибке получения страницы.
4. Добавить обезличенную структурную фикстуру в `tests/fixtures/news_sources/`,
   проверить текст, удаление навигации и стабильность повторного сбора
   в `tests/unit/clients/test_curated_news_sources.py`; обновить `verified_at`.
5. После выпуска backend выполнит миграции и seed. Источник появится
   выключенным; владелец задаст расписание и включит его в админке.

Изменение URL или правил текста инвалидирует условный HTTP-кеш профиля,
сохраняя исходную границу импорта, пользовательские настройки и историю.
Старый исследовательский список кандидатов остаётся отдельно от реестра.

## История обходов и отчёт запуска

В «Запуски → История обходов» каждая строка — попытка проверки одного
источника. Общий сбор может создать несколько строк с одним заданием.
Переход из строки открывает существующую страницу задания
`/admin/news/jobs/{job_slug}`: прогресс, время, параметры и отдельные
сводки по источникам, затем постраничный список результатов.
Фильтры выбирают источник, новые/обновлённые/неизменённые/пропущенные
материалы и записи с предупреждениями. У записи есть исходный адрес,
ссылка на карточку, причина, этап проблемы, признак сохранения предыдущего
текста и состояние анализа именно наблюдавшейся версии.

Снимки `news_source_runs` и `news_run_items` сохраняют результат обхода;
название и параметры источника не меняются в старом отчёте после правок
источника. Наблюдения записываются одной транзакцией с материалами и cursor,
с проверкой lease. История удаляется по обычному `history_retention_days`.
Пропущенные кандидаты не становятся редакционными материалами.
При HTTP 304 отчёт явно показывает отсутствие изменений в источнике.
При достижении лимита принятых материалов отмечается ограниченный объём
проверки; пропуски записываются до 200 строк, дальнейшее усечение обозначено
в отчёте. Количество публикаций за пределами просмотренной части неизвестно.

Адреса источников и заданий используют слаги. Имя источника и дата/время
заменяют внутренние номера в интерфейсе. Слаг источника остаётся стабильным
при переименовании; дата слага задания всегда рассчитывается по Самаре.
Числовые адреса и перенаправления не предусмотрены. Выпуск со слагами
устанавливался на пересозданную БД по отдельному решению владельца;
[инструкция](deployment.md#чистая-бд-для-выпуска-со-слагами) относится к нему.
Обновление проверенного каталога и расписаний (`0010`) не требует сброса БД.

## Обследование перед реализацией

Существующий FastAPI backend уже содержит PostgreSQL, Alembic,
`async_session_factory`, защиту `require_admin`, проверку Origin и no-store
для `/api/admin/*`. Он служит фасадом `news-analyzer-api`; отдельный публичный
API и ещё один сервер не требуются. APScheduler запускается только процессом
`news-analyzer-scheduler` из того же backend-образа. Долговечная очередь
и расписание хранятся в PostgreSQL, а не в памяти HTTP-воркера.

Точки изменения:

- `backend/src/db/models/news_*.py`, миграция после `20261008_1201`:
  источники, темы/рубрики и связи, материалы, анализы, задания, история
  обходов, редакционные решения и настройки.
- `backend/src/repositories/news_*.py`, `services/news_*.py`,
  `schemas/news.py`, `dependencies/news.py`, `api/news.py`, `main.py`:
  слоистый Admin API, короткие транзакции, защищённые изменения.
- `backend/src/clients/news_http.py`, `news_sources.py`, `llm.py`:
  безопасное получение внешних страниц, адаптеры и LLM-клиент.
- `backend/src/core/news_settings.py`, `background_tasks/news_scheduler.py`:
  конфигурация, отдельный scheduler, lease/heartbeat и восстановление.
- `frontend/src/app/(admin)/admin/news/`, `components/admin/news/`,
  `lib/news-api/`: редакционный центр в существующем AdminShell.
- Compose, примеры env, README, API-контракт, план реализации и тесты.

LLM-клиент адаптирован из `vera_rag_service/LLM_CLIENT_REFERENCE.md`.
По прямому поручению владельца локальные параметры провайдера берутся
из `.env` того проекта, профиль фонового обогащения. Секрет копируется
только в игнорируемый `backend/.env.dev`; в документации, API и логах его нет.
По уточнению владельца отдельный учёт расходов, резервирование бюджета
и денежные лимиты не реализуются. Клиент переносится с минимальной
адаптацией; модель задаётся одной переменной env, первоначально недорогая
Qwen при наличии у этого провайдера. Сохраняются обычные таймауты,
ограниченные retries и ограничение числа материалов за один проход.

Анализ уже выполняется асинхронно отдельными обработчиками. Их число задаёт
`NEWS_LLM_CONCURRENCY` (от 1 до 4, по умолчанию 1): тот же предел применяется
при атомарном захвате заданий в PostgreSQL и к пулу HTTP-соединений с LLM.
Для четырёх одновременных запросов установить `NEWS_LLM_CONCURRENCY=4`
в серверном env и пересоздать backend и `news-analyzer-scheduler`.
Смена env не требует пересборки образа, но код должен поддерживать значение 4;
обычный restart без пересоздания новое значение не применит.
Запускать второй scheduler для ускорения не требуется. Ограничения провайдера
проверяются отдельно; ошибки 429/5xx обрабатываются ограниченными повторами.

## План публикаций

Вкладка **«План публикаций»** находится внутри редакционного центра по
`/admin/news/plan`; отдельного пункта в общей навигации админки нет.
В подборке или на странице материала нажмите **«Добавить в план»**.
Кнопка видна сразу, раскрывать
редакторскую форму не требуется. План показывает заголовок, выжимку,
первоисточник, оценки, выбранное назначение и комментарий редактора.

Подборки и план отображаются списком: один материал занимает отдельную
строку с разделителем. Выжимка и оценки не обрезаются; источник, даты,
состояние анализа, предупреждения и редакторские действия сохранены.
Текст занимает всю ширину строки, действия расположены под ним.
Кнопки и закрытое редакторское решение стоят рядом, если хватает места;
раскрытая форма занимает отдельную строку. Отступы между блоками уменьшены.

План хранится в PostgreSQL через существующее решение `in_work`;
материалы, ранее отмеченные «В работу», уже входят в него. Используется
`GET /api/admin/news/items?decision=in_work` с обычной пагинацией.
Один материал отображается один раз независимо от числа решений в истории;
его данные и текущий анализ читаются из исходной записи.

В «Редакторском решении» можно изменить назначение (статья или короткая
новость) и комментарий, затем нажать «Сохранить изменения в плане».
«Убрать из плана» переводит материал в `deferred`; исходный материал,
анализ и история остаются доступны, его можно добавить снова.
«Отклонить» также исключает материал из плана. Добавление в план само
по себе не создаёт контент сайта и не публикует его.

## Внутренний контракт MVP

Все маршруты ниже имеют префикс `/api/admin/news`, существующие session
cookie, Origin-проверку для изменений и запрет кэширования. ID — целые
положительные числа, даты — ISO 8601 UTC. Пагинация: `items`, `total`,
`page`, `page_size`; максимум 50 строк. Справочники возвращаются массивами.

| Метод и путь | Назначение |
|---|---|
| GET `/sources`, GET/PATCH `/sources/{source_slug}` | Проверенные источники, включение и личное расписание |
| GET/POST `/topics`, PATCH `/topics/{id}` | Темы |
| GET/POST `/categories`, PATCH `/categories/{id}` | Рубрики |
| GET `/items`, GET `/items/{id}` | Подборки и карточка материала |
| POST `/items/{id}/decision` | Редакционное решение |
| POST `/items/{id}/reanalyze` | Повторный анализ (202) |
| POST `/jobs/collect`, GET `/jobs/{job_slug}` | Ручной сбор (202), прогресс/предпросмотр |
| GET `/collection-status` | Восстанавливаемый общий прогресс сбора и анализа, состояния источников |
| GET `/jobs/{job_slug}/runs`, GET `/jobs/{job_slug}/items` | Обходы источников и результаты обработки материалов |
| GET `/runs` | История обходов |
| GET/PATCH `/settings` | Общая пауза, политика, веса и лимиты |

Асинхронный ответ: `{"job_id": 1, "job_slug": "all-sources-2026-10-15-080000", "status": "queued"}`. Задание содержит
`id`, `slug`, `kind` (`collect`, `discover`, `analyze`), `status`, `source_id`, `source_slug`, `source_name`,
`item_id`, `attempts`, `progress`, `error`, `result`, даты и heartbeat.
Ошибки — короткие безопасные сообщения, без тел ответов провайдера.

Источник: `id`, `slug`, `name`, `description`, `url`, `active`, `schedule`,
`next_check_at`, `last_success_at`, `last_error`, `last_new_count`, `health`.
Админка меняет только включение и расписание. Адрес и правила сбора
задаются проверенным профилем в `backend/src/news_sources/`.

Тема/рубрика: `id`, `name`, `description`, `active`. Решение:
`decision` (`in_work`/`deferred`/`rejected`), `format`
(`longread_candidate`/`short_news_candidate`), `comment` (до 2000 символов).
Редактор всегда берётся из сессии, а не из тела запроса.

Карточка списка: `id`, `source_id`, `source_name`, `source_slug`, `url`, `canonical_url`,
`title`, `excerpt`, `published_at`, `first_seen_at`, `last_seen_at`,
`updated_at`, `status` (`pending_analysis`/`analyzed`), `duplicate_of_id`,
`analysis_state` (`analyzed`/`queued`/`running`/`failed`/`insufficient_text`/`pending`),
`analysis_error`, `collection_warning` (безопасные строки либо null),
`analysis` (null либо результат), `decision` (null либо последнее решение).
`status` сохраняет прежний контракт фильтра; фактическое состояние обработки
показывает `analysis_state`. `pending` означает отсутствие задания в очереди,
`failed` — завершившуюся ошибкой попытку, `insufficient_text` — нехватку текста.
Состояние учитывает последнее задание для текущего хеша содержимого, даже
если предыдущий результат `analysis` ещё сохранён.
Анализ: `id`, `is_relevant`, `category_id`, `category_name`, `topics`,
`suggested_topics`, `scores`, `summary_ru`, `editorial_comment_ru`,
`recommended_formats`, `confidence`, `needs_verification`, `news_score`,
`article_score`, `model`, `prompt_version`, `created_at`.
Подробная карточка дополнительно содержит `content`, `analysis_history`
и `decision_history`. Фильтры: `source_slug`, `category_id`, `topic_id`,
`format`, `status`, `decision`, `min_score`, `date_from`, `date_to`, `page`.
Без фильтра format показываются и ещё не разобранные материалы.

Общие настройки: `enabled`,
`editorial_policy`, `exclusions`, `news_weights`, `article_weights`
(ключи `topical_fit`, `significance`, `freshness`, `article_potential`,
сумма каждого набора 100), `initial_lookback_days`, `max_items_per_source`,
`max_excerpt_chars`, `analysis_batch_size`,
`text_retention_days`, `history_retention_days`. GET дополнительно содержит
безопасные `llm_configured`, `llm_provider`, `llm_model`.
Ключ и URL с учётными данными не выдаются.

## Критерии проверки

Обязательны PostgreSQL-тесты дедупликации, lease/recovery, двух scheduler;
RSS/304/HTML/SSRF/redirect/robots; ошибки и валидация
LLM; авторизация и Origin для всех API; реальные UI-сценарии с клавиатурой,
состояния ожидания/ошибки, две темы и мобильная раскладка. API/парсеры
проверяются на контролируемых фикстурах, не зависящих от внешних сайтов.

## Запуск и повседневная работа

Команды установки, начальные справочники и env приведены в
[README](../README.md#news-analyzer). В production backend применяет все
миграции и seed до запуска scheduler. Оба процесса используют один образ
и одну БД; HTTP-сервер сам очередь не обрабатывает. В dev Compose backend
тоже выполняет миграции и seed автоматически; при прямом запуске Python
они выполняются вручную по README. Для просмотра состояния
production-контейнеров:

```bash
docker compose --env-file backend/.env.production -f docker-compose.yml ps
docker compose --env-file backend/.env.production -f docker-compose.yml logs --tail 50 news-analyzer-scheduler
```

В `/admin/news/sources` находится компактная таблица проверенных источников:
название, краткое описание, переключатель регулярных проверок, личное
расписание и следующая проверка. Расписание открывается в модальном окне.
Отдельного подключения, форм URL/CSS и названий парсеров нет.
Для источника доступны ручная проверка и история; сверху можно проверить
все включённые источники. Результат открывается в существующем отчёте
задания. Над таблицей и в истории запусков виден общий ход проверки:
проверенные источники, новые/изменённые материалы и отдельно готовые анализы.
Строки таблицы показывают очередь, текущую проверку, результат или причину ошибки.
Открытую вкладку разрешается закрыть: очередь находится в PostgreSQL.

Прогресс восстанавливается с сервера при открытии страницы. Во время работы
он обновляется каждые 2,5 секунды, после завершения — каждые 15 секунд;
скрытая вкладка приостанавливает опрос и обновляет состояние при возвращении.
При потере связи сохраняется последнее полученное состояние с возможностью
повторить запрос. Завершение сбора и анализа показывается раздельно.
В анализ входят только новые и изменённые версии; неизменённые материалы
не создают ложный объём работы. Пауза, отсутствие модели, недостаточный
текст и недоступная версия объясняются без бесконечного индикатора работы.
Новые ручные задания сохраняют выбранный набор источников при постановке
в очередь; смена переключателей не изменяет уже принятый набор.

Каждый профиль в `backend/src/news_sources/` содержит фиксированные правила
списка и текста публикации для своего RSS/Atom или HTML. Новые профили
добавляются через код после проверки реальных страниц и повторного сбора.
Исследовательский JSON с 98 кандидатами не определяет доступный каталог;
справочные/API-ресурсы и непроверенные сайты не показываются в админке.

После миграций `python -m scripts.seed_news` синхронизирует метаданные
профилей и создаёт отсутствующие темы/рубрики. Новый источник выключен,
его рекомендуемое расписание можно изменить до включения. При повторном
старте сохраняются включение, пользовательское расписание, слаг и история;
неизменённые записи не перезаписываются. Исключённый из реестра профиль
перестаёт участвовать в сборе, его история сохраняется.

Расписание индивидуально: ежедневно в выбранные часы, каждые N дней
от выбранной даты или по выбранным дням недели. Время — Самара (UTC+4),
в БД `next_check_at` и даты заданий хранятся в UTC. При включении и смене
расписания следующая проверка назначается строго в будущем. Планировщик
опрашивает календари в пределах `NEWS_SETTINGS_REFRESH_SECONDS` (30 секунд).
После простоя ставится не более одного актуального обхода на источник;
два scheduler и перезапуск не дублируют одно календарное начало.
Выключение источника, смена расписания и общая пауза отменяют устаревшие
ожидающие автоматические задания. Уже начатая работа завершается с
обычными проверками lease и неизменности конфигурации.

Общая пауза также останавливает постановку новых автоматических анализов.
Ручной сбор и повторный анализ доступны независимо от неё и не ждут
расписания. Новые материалы сначала сохраняются, затем отдельные задания
передают их модели. Завершение сбора не означает завершения анализа.
«Все материалы» включает материалы без анализа; подборки показывают
соответствующие рекомендации. При нехватке текста сначала нужен повторный
сбор, затем анализ; ошибки доступны в карточке и отчёте обхода.

## Модель и повторная обработка

Текущая локальная модель — `qwen/qwen3-30b-a3b-instruct-2507` через Polza.
Это сменная начальная конфигурация: окончательный выбор остаётся владельцу.
Клиент получает уже собранный текст, а не ищет материалы в интернете.
Версия запроса `news-v3` ограничивает аннотацию 500 символами, комментарий
редактора — 600 и запрещает восполнять недостающие факты по заголовку или
знаниям модели. Доверенная редакционная политика передаёт `analyzed_at`,
`current_date` в UTC и рассчитанный сервером `server_freshness`.
Сервер заменяет модельную оценку `scores.freshness` своей перед расчётом
двух взвешенных рейтингов:

| Возраст публикации на момент анализа | `freshness` |
|---|---|
| Не более 1 / 3 / 7 / 14 / 30 суток | 100 / 90 / 75 / 50 / 25 |
| Старше 30 суток, неизвестная или некорректная дата | 0 |
| Дата более чем на сутки в будущем | 0 |

Допуск до суток в будущем учитывает расхождение часов источника; в этом
пределе оценка равна 100. Возраст считается по времени UTC, границы включены.

`NEWS_LLM_API_KEY`, `NEWS_LLM_API_URL`, `NEWS_LLM_MODEL` и
`NEWS_LLM_PROVIDER` задаются только на сервере. После изменения env
пересоздайте backend и scheduler, как показано в README. Статус «Настроена»
означает наличие конфигурации; доступность провайдера проверяется запросом.
Расходные счётчики, денежные квоты и резервирование бюджета отсутствуют.

Одинаковое содержимое повторно не анализируется. Изменение содержимого
создаёт новое задание; старые результаты сохраняются. Изменение модели,
политики или весов само по себе не пересчитывает уже разобранный архив:
используйте «Повторить анализ» в нужной карточке.

Идентичность результата — материал, хеш содержимого, модель и версия
запроса. Явный повтор с той же идентичностью обновляет результат и дату;
факт запуска остаётся в заданиях. Другая модель, версия или содержимое
создают отдельную запись истории. Отдельной версии на каждое нажатие нет.
Редакторские решения сохраняются отдельной историей с автором из сессии.

### Восстановление ранее собранных материалов

Из каталога `backend`, с серверной конфигурацией выбранного окружения:

```bash
python -m scripts.repair_news --source-id 1
python -m scripts.repair_news --source-id 1 --item-id 42
python -m scripts.repair_news --source-id 1 --apply
```

Без `--apply` команда только показывает план (dry run), не создаёт заданий
и не меняет материалы. `--item-id` ограничивает обработку выбранным
материалом источника. `--apply` ставит долговечные задания `collect`
с `repair_item_ids`, пакетами до 50 ID. Отдельный scheduler повторно получает
текст по уже сохранённым URL; новые материалы не создаются, старые не
удаляются. При достаточном тексте и настроенной модели ставится явный
повтор анализа по `news-v3`, включая материалы с прежним анализом.
Редакторские решения и история других версий сохраняются.

После обновления кода требуется перезапуск отдельного scheduler;
reload API не обновляет обработчик. Эта команда сама не развёртывает
изменения и не восстанавливает production без её запуска в нужном окружении.

## Сбои, ограничения и хранение

Без ключа материалы остаются в `pending_analysis`. Ошибки сети, 429/5xx
и некорректный JSON проходят ограниченные повторные попытки. После
исчерпания попыток задание видно как ошибочное; сохранённый материал
доступен для ручного повторного анализа. Постоянные ошибки 4xx не
повторяются внутри клиента. В логах нет ключей, запросов и тел ответов LLM.

При перезапуске scheduler забирает сохранённую очередь; просроченный lease
восстанавливается с учётом лимита попыток. Пока lease действует, второй
процесс не получает это задание. Heartbeat и проверка владельца при записи защищают
от сохранения результата устаревшим обработчиком. Пропущенные слоты
расписания объединяются в последний актуальный обход.

Начальные ограничения: первые 30 дней, до 50 материалов за обход
источника, до 3000 символов фрагмента, до 20 постановок анализа за пакет.
Граница начального периода сохраняется как `source.cursor.initial_cutoff_at`
и не сдвигается при следующих обходах или изменении `initial_lookback_days`.
Повторные обходы не добавляют неизвестные архивные публикации старше
этой границы; уже известные URL могут обновляться.

Минимум для анализа — 200 символов очищенного текста. При догрузке страницы
выбирается основной содержательный блок, а не первый `article` из меню;
навигация исключается. Неудачная догрузка или слишком короткий текст
не заменяют ранее сохранённый качественный текст и его анализ.
Такие случаи видны как `collection_warning`, источник получает
`health=degraded` («Есть предупреждения»), а счётчик `warnings` отражает
предупреждения сбора. ETag/Last-Modified проблемного обхода не фиксируются,
чтобы следующий запрос мог повторить получение текста.
Сбор не обходит robots.txt, защиту сайтов и страницы, требующие JavaScript.
HTML — best effort с настраиваемыми селекторами; сложному сайту нужен
отдельный адаптер. Ошибочный источник не мешает сохранить результаты
успешных источников.

HTTP-клиент принимает `gzip` (включая `x-gzip`) и `deflate` (zlib/raw).
`NEWS_HTTP_MAX_RESPONSE_BYTES` (по умолчанию 2 МиБ) ограничивает **и скачанные,
и распакованные** байты независимо друг от друга. Распаковка потоковая,
с ограничением выделяемого объёма; повреждённые и оборванные потоки
отклоняются. Brotli, Zstandard и многослойное сжатие не поддерживаются.
Проверки DNS/IP, TLS, robots.txt и перенаправлений действуют также для лент
и отдельных страниц материалов. Недоступный robots.txt обозначается
отдельно от явного запрета обхода; ни один из этих случаев не обходится.

При автоматическом разборе HTML используются заголовки и даты карточек,
сохраняются заголовки внутри `article`; навигация и ссылки на файлы не
считаются публикациями. Статический HTML внутри `noscript` можно разобрать
без исполнения JavaScript. Если опубликованная на странице RSS/Atom-лента
недоступна, но HTML содержит карточки, предпросмотр возвращает их с
предупреждением. Явно выбранный RSS не подменяется HTML.

Фоновая очистка выполняется раз в час. По умолчанию текст удаляется через
90 дней без повторного обнаружения, старые задания, обходы и история —
через 180 дней. Последние анализ и редакторское решение сохраняются.
Резервная копия общей БД включает редакционные данные; порядок описан в
[инструкции развёртывания](deployment.md).

## Проверка совместимости каталога

Повторяемый аудит использует тот же `NewsSourceClient` и HTTP-защиты, что
scheduler. Он проверяет все уникальные основные адреса, RSS и дополнительные
ссылки из каталога; дубли авторов сопоставляются с исходными строками.
Справочные сайты и API проверяются на доступность отдельно: HTTP 200 для
документации не означает наличия готового адаптера API.

Из корня проекта (PowerShell, Python-окружение backend активировано):

```powershell
Set-Location backend
python -m scripts.audit_news_catalogue --catalogue src/data/news_source_catalogue.json --output "$env:TEMP/news-catalogue-audit.json" --collect --repeat-collect
```

Это чтение внешних ресурсов без записи источников/материалов в БД и без LLM.
`--collect` дополнительно получает до трёх материалов каждого найденного
источника, включая попытку загрузить текст; для проверки старых блогов
используется окно 3650 дней, рабочая настройка 30 дней не меняется.
Ошибка догрузки текста сохраняется в `collection.warnings`, ошибка этапа
сбора — в `collection.status`; успешный предпросмотр от этого не становится
успешной проверкой текста. `passed` означает непустой пакет с достаточным
текстом без предупреждений; `degraded` — проблемы хотя бы у одного материала,
`empty` — пустой пакет, `not_modified` — ответ 304 без проверки текста.
Предпросмотр содержит до пяти карточек.

`--repeat-collect` требует `--collect` и выполняет второй безусловный сбор
с той же временной границей и известными URL первого пакета. Отдельные
`collection` и `repeat_collection` показывают качество каждого прохода;
`collection_summary` сводит их результаты отдельно от discovery. В
`comparison` сравниваются нормализованные canonical URL и хеши текста:
`new`, `disappeared`, `changed`, `unchanged`. Изменение текста само по себе
не считается дублем. Общий canonical у разных URL отмечается как
`ambiguous` с предупреждением, а не как успешная стабильность.
По умолчанию одновременно проверяются до пяти адресов, общий предел на
адрес — 120 секунд; обычные лимиты HTTP-клиента сохраняются. Завершение
команды означает завершение аудита: результаты надо смотреть в `summary`
и `results`, включая `failed`/`error`.

Для адресного повторения: `--only labs-deepmind,labs-anthropic`. Необязательный
`--documents-dir /tmp/news-audit-documents` сохраняет публичные документы
для локального разбора; их не следует добавлять в git. JSON-отчёт содержит
короткие предпросмотры и разрешённые HTTP-заголовки, без cookies и секретов.

Найдены и исправлены общие причины ошибок:
