# AGENTS.md — BKS Lab

## О проекте

**BKS Lab** — личный сайт-портфолио и блог владельца (bks-lab.ru): проекты,
современная разработка, архитектура, управление IT-проектами, AI, доступность
и авторские материалы.

Это **личный проект**, не корпоративный. Отсюда жёсткие ограничения:

- **Никаких интеграций с Bitrix24.** Скиллы `bitrix-*` в этом проекте не
  использовать, ни в коде, ни в процессах. Задачи и коммуникация по этому
  проекту в Bitrix24 не ведутся.
- Нет корпоративных систем, внешних заказчиков и стейкхолдеров — решения
  принимает владелец проекта.
- Не добавлять зависимости и интеграции «на вырост» без согласования.

## Текущее состояние и границы работы

На 08.10.2026 реализованы публичный сайт, собственная админка и MVP
News Analyzer. Автоматические проверки и локальная интеграционная приёмка
завершены; результаты и ограничения зафиксированы в README и
`docs/implementation_plan.md`.

Владелец отложил публичный запуск, настройку production-сервера/DNS/TLS,
рабочей почты и контактов, включение РСЯ и полную ручную приёмку
доступности. Не возвращать эти шаги в активную работу без нового поручения
и не отмечать их выполненными. Статусы `[~]` в плане могут отражать эту
отложенную приёмку при готовой реализации.

Sentry, CMS/upload Markdown, SearXNG, генерация текстов, SEO-анализ
найденных новостей и автопубликация не входят в текущий объём. Обычные
metadata/OG/sitemap самого сайта уже реализованы.

## Стек

- **Backend:** Python 3.12, FastAPI, Hypercorn, Pydantic v2 + pydantic-settings.
  Слоистая архитектура: `api → services → repositories → {content | PostgreSQL}`.
  Контент трёх типов (статьи, заметки, проекты) — Markdown-файлы с
  frontmatter, источник истины; в PostgreSQL автоматически синхронизируется
  read-model `content_items` (метаданные + plain text) для админки и
  будущего анализа агентами. PostgreSQL 16 (async SQLAlchemy + asyncpg,
  Alembic) в отдельном контейнере, как в референсе — статистика посещений,
  подписчики, проекция контента, админ-сессии. Админка — **собственный
  фронт** (`/admin` в Next.js) + закрытое Admin API (`/api/admin/*`,
  серверная сессия в httpOnly-cookie, один админ из `.env`); sqladmin не
  используем. Тесты: pytest + httpx.
- **Frontend:** Next.js 16 (App Router) + React 19 + TypeScript, Tailwind CSS 4.
  SSG/SSR, React Router не используется (роутинг Next.js). Тесты: Vitest +
  Testing Library. Стек утверждён владельцем как осознанное отклонение от
  дизайн-ТЗ §2 («React + JavaScript») в пользу SEO и SSG, см.
  `docs/architecture.md` §4.
- **News Analyzer:** закрытое API `/api/admin/news/*` в существующем FastAPI
  и отдельный процесс `news-analyzer-scheduler` из того же backend-образа.
  APScheduler, долговечная очередь PostgreSQL, RSS/Atom и HTML, внешняя LLM.
  Источники, анализы и решения находятся в БД отдельно от Markdown-публикаций.
- **Инфраструктура:** Docker Compose: dev — db/backend/scheduler; prod
  дополнительно frontend/nginx/certbot. Один nginx для TLS и reverse proxy.
  Нет Celery, Redis/RabbitMQ и второго nginx; PostgreSQL-очередь News Analyzer
  является согласованной частью проекта. У scheduler нет публичного порта.

## Обязательные требования

- **WCAG 2.2 AA** — не опция, а критерий приёмки (см. дизайн-ТЗ §14, §22, §23).
- Семантический HTML5, один `<main>` и один H1 на страницу, skip-link.
- Не менять без согласования: знак «лупа + `</>`», название BKS Lab, палитру
  navy/cyan, структуру главной и блога, тексты CTA (дизайн-ТЗ §24).
- Согласованное направление: светлые основные поверхности и отдельная
  тёмная тема. Фирменный знак/вывеска должны выглядеть частью оформления
  стены в соответствующем блоке, а не отдельной карточкой с картинкой.
- Не использовать emoji как UI-иконки; не генерировать «похожие» логотипы в
  коде — использовать существующие файлы `frontend/public/brand/`.
  Готовые изображения находятся в `frontend/public/images/`; не запускать
  `frontend/scripts/generate_placeholders.py` поверх них — он перезаписывает ассеты.
- Рекламные блоки (Яндекс.РСЯ) — только через компонент `AdSlot`: фиксированная
  высота против CLS, `<aside aria-label="Реклама">`, не внутри текста статей,
  на главной рекламы нет, в dev отключены флагом.
- Публикуемый контент редактируется только через Markdown-файлы в git;
  витрины контента, статистики и подписчиков в админке — read-only.
  По отдельному ТЗ `search_news/BKS_Lab_News_Analyzer_TZ.md` редакционный
  центр управляет источниками, справочниками, настройками и решениями
  о найденных новостях; автопубликации и записи в Markdown из него нет.
  LLM-клиент — по референсу `vera_rag_service/LLM_CLIENT_REFERENCE.md`;
  по уточнению владельца отдельный учёт расходов и бюджетный модуль не нужны.
  Все эндпоинты `/api/admin/*` — только за `require_admin`; новые админские эндпоинты
  добавлять исключительно под префикс `/api/admin`, не в публичное API.

## News Analyzer: сохранять принятые решения

- Минимально адаптированный референсный клиент; никаких счётчиков расходов,
  денежных квот и резервирования бюджета. Обычные таймауты, ограниченные
  retries и технические ограничения объёма сохраняются.
- Модель классифицирует собранные фрагменты. Ответ проверяется Pydantic,
  категории/темы выбираются по существующим ID, рейтинги считает сервер.
- Сначала сохранять материал, затем анализировать отдельным заданием.
  Без ключа или при ошибке LLM материал остаётся доступным для повторной обработки.
- Scheduler не запускать внутри FastAPI или Next.js. Сохранять атомарный
  claim, дедупликацию расписания, lease/heartbeat и проверку владельца при записи.
- Источник сохраняется только после соответствующего успешного discovery.
  Каталог — подсказки; seed создаёт темы/рубрики, а не активные источники.
- Внешние страницы недоверенные: проверять публичные IP, DNS и редиректы,
  соблюдать robots.txt, лимиты и TLS; не исполнять JS и не обходить защиту сайта.
- Админские мутации требуют session cookie и точный Origin; ответы no-store.
  Не включать ключи, провайдерские ответы и запросы модели в логи или коммиты.

## Процесс

- Реализация ведётся по этапам из `docs/implementation_plan.md`; каждый этап
  закрывается проверками, указанными в его Definition of Done.
- **Backend — FastAPI.** При разработке и ревью бэкенда обязательно
  используй скилл `fastapi-patterns` (user scope) вместе с
  `docs/FASTAPI_PATTERNS.md`: слои, DI, исключения, тесты — по ним.
- **Frontend — Next.js.** При разработке и ревью фронтенда используй скилл
  `next-js`; при проектировании и визуальном ревью UI — `frontend-design`
  (с учётом дизайн-ТЗ).
- Поручение реализации ведётся по скиллу `dev-pipeline` (режим по размеру
  этапа); ревью готовых изменений — `code-review`.
- Код на русском не пишем (комментарии/идентификаторы — английский);
  пользовательские тексты интерфейса и контент — русский.
- Коммиты и push — только по явному разрешению владельца.
- Перед сдачей фронтенд-этапа — прогон чек-листа доступности (дизайн-ТЗ §22)
  в применимой части и отчёт, что именно проверено.
- Использовать актуальные результаты проверок; документационные правки
  сами по себе не требуют повторного запуска всех тестов. Команды — в README.
- После правок кода scheduler требуется перезапуск отдельного процесса;
  изменение env требует пересоздания backend и scheduler. Reload API не
  обновляет запущенный обработчик.
