# BKS Lab — News Analyzer
Техническое задание агенту-разработчику. Версия 1.0, 08.10.2026.

## Цель
Отдельный сервис в Docker Compose трижды в сутки в фоне проверяет заданные источники, получает только новые/изменённые материалы, сохраняет в PostgreSQL и передаёт внешней LLM на оценку. В самописной админке редактор видит заголовок, источник, ссылку, дату, рубрику, темы, краткую аннотацию, рейтинг и объяснение соответствия тематике BKS Lab. Два назначения: материал для большой статьи и кандидат для короткой новостной ленты. Автопубликации нет.

## Жёсткие ограничения
Без Celery, Redis-брокера, локальных LLM и обязательных платных поисковых API. Использовать APScheduler в отдельном процессе, PostgreSQL как хранилище заданий, httpx, адаптеры источников. Внешняя LLM по API с конфигурируемым провайдером и бюджетными лимитами. SEO и генерация текстов — не MVP.

## Шаг 0: обследование репозитория
Изучить Compose, backend, frontend, админку, авторизацию, PostgreSQL, миграции, SQLAlchemy, тесты, логирование. Представить список файлов, миграций, маршрутов и точек интеграции до реализации. Сохранить существующий стиль и границы сервисов.

## Архитектура
- `news-analyzer-api`: защищённый API или фасад через существующий backend.
- `news-analyzer-scheduler`: отдельный процесс APScheduler из того же Docker-образа.
- PostgreSQL: источники, материалы, темы, рубрики, задания, анализ, история и редакционные решения.
- Адаптеры RSS/Atom и HTML в MVP; SearXNG и специальные API позже.
- Все долгие операции выполняются в фоне; ручной запуск создаёт запись задания и сразу возвращает HTTP 202 + job_id.
- API не публиковать наружу без необходимости.

## Планировщик
Три запуска в сутки по настраиваемому часовому поясу. APScheduler только в выделенном процессе, не в воркерах FastAPI. `max_instances=1`, `coalesce=True`; PostgreSQL advisory lock и атомарное получение заданий (`FOR UPDATE SKIP LOCKED`) для защиты от дублей. Таблица заданий со статусами queued/running/completed/failed/cancelled, lease/heartbeat, retries, счётчиками, ошибкой. Восстановление зависших заданий после рестарта. Лимиты параллельности: HTTP 5, LLM 1–2 (настраиваются). Сбор и AI-анализ — разные стадии: ошибка модели не теряет собранные данные.


## Адаптеры источников
| Тип | Метод | Этап |
|---|---|---|
| rss | RSS/Atom, GUID, ETag, Last-Modified | MVP |
| html | Список публикаций и CSS-селекторы | MVP |
| search | Self-hosted SearXNG, сохранённые запросы | После MVP |
| custom_api | Официальные бесплатные API | По необходимости |

Общий `CollectedItem`: external_id, url, canonical_url, title, description, content, published_at, updated_at, metadata. Общий интерфейс `discover(config)` (проверка и предпросмотр) и `fetch(source,cursor)` (обход).

### Добавление источника из админки
1. Название и URL/поисковый запрос.
2. Кнопка «Проверить»: HTTP-проверка, определение RSS/Atom по содержимому и `rel=alternate`, иначе HTML.
3. Предпросмотр 3–5 материалов с заголовком, датой, ссылкой.
4. Для HTML — настраиваемые item/title/link/date/content CSS-селекторы и повторный тест.
5. Выбор тем, рубрик, приоритета, активности, частоты; сохранить в БД.
6. Список источников: здоровье, последний успешный обход, новые записи, ошибки; кнопка «Проверить сейчас» ставит задачу в очередь.
Авторазбор HTML best effort; сложные сайты требуют отдельного Python-адаптера. Playwright не включать в MVP.

### Безопасность
Защита от SSRF: только http/https; запрет localhost, private/link-local/metadata IP и Docker-адресов; проверять DNS и каждый редирект. Таймауты, лимиты размера ответа, редиректов, content-type, частоты. Не исполнять JS, не обходить капчи; учитывать robots.txt, правила сайтов и авторские права. Контент источников считать недоверенным.

## Определение изменений
RSS: GUID, даты, ETag/Last-Modified; HTML: нормализованный/canonical URL и хеш очищенного текста; search: URL. Хранить first_seen_at, last_seen_at, published_at, updated_at раздельно. Уникальность по source+external_id либо source+normalized_url; выявлять совпадения между источниками. `content_hash` для существенных изменений. Не анализировать неизменённое повторно. Первый обход ограничить, например, 30 днями и 50 публикациями на источник. Не считать дату единственным признаком новизны. Cursor обновлять только после успешного сохранения.

## Подготовка текста
Без LLM удалить дубли и очевидный мусор. Если RSS-описания достаточно — не скачивать статью; иначе извлечь основной текст (`trafilatura` или аналог), удалить меню/рекламу/HTML. Передавать модели заголовок, источник, дату, URL, описание и до 3000 символов очищенного текста (конфигурируемо). Не отправлять полный HTML. Позднее улучшить выбор фрагмента по подзаголовкам и информативным абзацам.


## LLM-анализ
В MVP модель НЕ ищет в интернете; она классифицирует уже собранные материалы. Передавать описание BKS Lab, аудиторию, разрешённые темы и рубрики, критерии и исключения. Категории и темы выбирать по существующим ID; новые предложения — отдельно.

Пример JSON-ответа:
```json
{
  "is_relevant": true,
  "category_id": "existing-id",
  "topic_ids": ["existing-id"],
  "suggested_topics": [],
  "scores": {
    "topical_fit": 90,
    "significance": 82,
    "freshness": 95,
    "article_potential": 78
  },
  "summary_ru": "Краткая аннотация.",
  "editorial_comment_ru": "Почему подходит BKS Lab.",
  "recommended_formats": ["short_news_candidate", "longread_candidate"],
  "confidence": 0.86,
  "needs_verification": true
}
```
Pydantic-валидация; JSON Schema/structured output по возможности. Итоговый рейтинг вычисляет Python по весам из настроек, отдельно для коротких новостей и статей. Доверие к источнику хранить в БД. Модель не подтверждает достоверность фактов по одному фрагменту. Сохранять модель, версию промпта, usage, время, ошибки. Идемпотентность по item_id+content_hash+model+prompt_version. Ограниченные retries на 429/5xx и невалидный JSON. Лимиты токенов, запросов и бюджета; без ключа или при отказе API материалы остаются pending_analysis. Защита от prompt injection. Ручной повторный анализ.

## Таблицы
- `news_sources`: тип, URL/query, JSONB config, расписание, приоритет, доверие, ETag/cursor, статус.
- `news_topics`, `news_categories`, `news_source_topics`: справочники и связи.
- `news_items`: URL, заголовок, excerpt, даты, хеши, статусы.
- `news_analyses`, `news_analysis_topics`: результат LLM, рейтинги, темы, версия промпта, токены.
- `news_jobs`: очередь заданий, lease, попытки, прогресс.
- `news_source_runs`: история обходов и ошибки.
- `news_editorial_decisions`: в работу/отложено/отклонено, назначение, редактор.
- `news_settings`: политика, веса, лимиты и расписание (или существующий механизм).
Использовать Alembic, уникальные индексы для дедупликации, индексы по статусам, датам и рейтингам; retention текстов и истории. Не связывать найденный материал напрямую с опубликованной статьёй.


## API (адаптировать к маршрутам проекта)
| Метод | Маршрут | Назначение |
|---|---|---|
| GET | /news/sources | Источники и здоровье |
| POST | /news/sources/discover | Проверка/предпросмотр |
| POST | /news/sources | Добавление |
| PATCH | /news/sources/{id} | Редактирование/пауза |
| GET/POST/PATCH | /news/topics | Темы |
| GET/POST/PATCH | /news/categories | Рубрики |
| GET | /news/items | Подборка, фильтры, пагинация |
| GET | /news/items/{id} | Карточка и анализ |
| POST | /news/items/{id}/decision | Редакторское решение |
| POST | /news/items/{id}/reanalyze | Очередь анализа |
| POST | /news/jobs/collect | Ручной запуск, HTTP 202 |
| GET | /news/jobs/{id} | Прогресс |
| GET | /news/runs | История |
| GET/PATCH | /news/settings | Настройки |
Все API защищены существующей авторизацией. Фильтры: тема, рубрика, источник, период, рейтинг, формат, статус и решение.

## UI
«Редакционный центр»: вкладки «Для статей»/«Короткие новости»; карточки с заголовком, источником, датой, ссылкой, аннотацией, рубрикой, темами, рейтингом и комментарием LLM. Действия: «В работу», «Отложить», «Отклонить». Управление источниками с предпросмотром, темами/рубриками, настройками, историей запусков и ручным запуском. Следовать дизайну админки. Доступность: клавиатура, labels, видимый фокус, статусы для скринридеров, без зависимости от цвета.

## Compose и конфигурация
Два процесса из одного образа: news-analyzer-api и news-analyzer-scheduler; scheduler без публичного порта. Healthcheck, restart policy, graceful shutdown.
Env/secrets: DATABASE_URL, NEWS_TIMEZONE, NEWS_SCHEDULE, NEWS_HTTP_CONCURRENCY, NEWS_LLM_CONCURRENCY, NEWS_MAX_EXCERPT_CHARS=3000, NEWS_LLM_PROVIDER, NEWS_LLM_MODEL, NEWS_LLM_API_KEY, NEWS_LLM_DAILY_LIMIT, NEWS_LLM_MONTHLY_BUDGET, опционально SEARXNG_URL. Не логировать ключи. Логировать job_id, source_id, item_id, время, счётчики, ошибки, usage.

## Порядок реализации
1. **Аудит репозитория и каркас:** Compose, БД, миграции, задания, APScheduler, блокировки, healthcheck.
2. **Сбор:** RSS/HTML, предпросмотр, CRUD источников, безопасность HTTP, дедупликация, история.
3. **AI:** подготовка фрагментов, внешний провайдер, схема ответа, рейтинги, лимиты, retries.
4. **Админка:** подборки, карточки, фильтры, решения, источники, настройки и история.
5. **Эксплуатация:** тесты, документация, логирование, проверка восстановления.
6. **После MVP:** SearXNG, поисковые темы, объединение новостей об одном событии, SEO, черновики и интеграция CMS.

## Тесты и приёмка
Тестировать RSS GUID/ETag/304, HTML-селекторы, дубли, одинаковые URL из двух источников, 429/500/timeout, SSRF и redirect, два scheduler одновременно, рестарт во время задачи, невалидный ответ LLM, превышение бюджета, отсутствие ключа, авторизацию API, пагинацию, редакционные решения и клавиатурную доступность.

**Definition of Done:** Compose поднимается; плановые обходы работают без открытой админки; источник добавляется и тестируется через UI; повторный обход не создаёт дублей; материалы сохраняются до вызова LLM; результаты LLM валидируются и ранжируются; редактор видит две подборки и первоисточники; сбои не приводят к потере материалов; автопубликации нет; миграции, тесты и README готовы.

## Правила агенту
Работать по этапам; не добавлять лишние зависимости; не заменять APScheduler на Celery; не добавлять локальную LLM; не подключать платные поисковые API. Не принимать самостоятельно продуктовые решения о провайдере LLM и SEO. Сначала изучить существующий код. После каждого этапа кратко сообщать: что сделано, какие файлы изменены, какие тесты запущены, что осталось и какие решения требуют согласования.
