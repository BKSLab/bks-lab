# BKS Lab

Личный сайт-портфолио и блог (bks-lab.ru): статьи, заметки, проекты,
статистика посещений, админка и редакционный News Analyzer для владельца.

## Возможности и состояние

- Главная, блог с поиском и рубриками, заметки, проекты, страницы об авторе
  и контакты. Светлая базовая тема, тёмная тема, фирменные изображения и
  вывеска BKS Lab в оформлении страницы.
- Подписка, форма обратной связи с хранением обращений в БД, статистика посещений,
  metadata/Open Graph и sitemap. Рекламные места подготовлены, РСЯ выключена.
- Закрытая панель `/admin`: обзор, статистика, подписчики, обратная связь и редактор
  публикаций (создание и правка материалов, изображения, версии,
  вкладки «Текст/Предпросмотр/Настройки», панель действий при выделении,
  браузерная проверка орфографии RU/EN).
- Редакционный центр `/admin/news`: RSS/Atom и HTML-источники с предпросмотром,
  фоновый сбор, анализ внешней LLM, подборки для статей и коротких новостей,
  решения редактора, история и настройки. Подходящие новые материалы могут
  автоматически становиться короткими «Заметками на полях» через очередь
  с паузой, интервалом публикации и сроком актуальности.

**На 08.10.2026 согласованная функциональность реализована и проверена
локально, включая отдельный production-стенд с HTTPS.** Позже добавлен
редактор публикаций в админке (см. «Контент»); автоматические проверки
пройдены, ручная приёмка редактора не проводилась. На 13.10.2026 серверный
стенд по IP запущен, вход в админку проверен; подготовлен переход на
`http://bks-lab.ru`, ожидается обновление DNS. HTTPS, активация РСЯ и полная
ручная приёмка доступности ещё не выполнены. Автоматические проверки
не означают, что эти пункты выполнены. Sentry, внешняя CMS, SearXNG и
генерация полноразмерных статей остаются за пределами текущего MVP.

## Стек

- **Backend:** Python 3.12, FastAPI, Hypercorn, Pydantic v2 + pydantic-settings,
  SQLAlchemy 2 (async) + asyncpg, Alembic, PostgreSQL 16.
- **Frontend:** Next.js 16 (App Router) + React 19 + TypeScript, Tailwind CSS 4.
- **News Analyzer:** RSS/Atom и HTML, внешняя LLM, очередь в PostgreSQL,
  APScheduler в отдельном процессе `news-analyzer-scheduler`.
- **Инфраструктура:** Docker + Compose (dev: `db`, `backend`,
  `news-analyzer-scheduler`; prod дополнительно frontend и nginx:
  стенд по IP и переход на домен — HTTP, HTTPS/certbot — после выпуска сертификата).
  Production env — `backend/.env.production`, dev env —
  `backend/.env.dev`. Новых открытых портов для News Analyzer нет.

Документация: `docs/architecture.md`, `docs/api_contract.md`,
`docs/content_format.md`, `docs/content_editor.md`,
`docs/implementation_plan.md`, дизайн-ТЗ —
`BKS_Lab_frontend_design_spec.md`. Запуск на сервере, публикация контента,
резервные копии и сертификаты: [docs/deployment.md](docs/deployment.md).
Редакционный центр и фоновый сбор: [docs/news_analyzer.md](docs/news_analyzer.md).

## Быстрый старт (dev)

Требования: Docker, Python 3.12, Node.js 22.22.2+ (ветка 22) или 24.15+
(ветка 24). Эти версии поддерживают серверную санитизацию HTML публикаций.

1. Подготовить конфигурацию бэкенда:

   ```bash
   cp backend/.env.dev.example backend/.env.dev   # затем заполнить значения
   ```

   Для процессов в Docker использовать `POSTGRES_HOST=db`,
   `POSTGRES_PORT=5432` в `backend/.env.dev`. При прямом запуске Python
   переопределять их на `localhost:5434` переменными окружения.

2. Поднять БД, бэкенд и фоновый обработчик в Docker:

   ```bash
   docker compose -f docker-compose.dev.yml up -d --build db backend news-analyzer-scheduler
   curl http://localhost:8000/api/health   # {"status":"ok"}
   ```

   PostgreSQL доступен с хоста на порту 5434 (для IDE). Код бэкенда
   смонтирован в контейнер: HTTP-сервер подхватывает правки через `--reload`.
   После изменения кода фонового обработчика перезапустите
   `docker compose -f docker-compose.dev.yml restart news-analyzer-scheduler`; после изменения env
   пересоздайте контейнеры.

   Локальный запуск бэкенда без Docker (против Docker-БД):

   ```bash
   cd backend
   pip install -r requirements-dev.txt
   hypercorn main:app --reload --bind 127.0.0.1:8000   # POSTGRES_HOST=localhost POSTGRES_PORT=5434
   ```

3. Запустить фронтенд локально:

   ```bash
   cd frontend
   cp .env.example .env.local   # при необходимости
   npm ci
   npm run dev                  # http://localhost:3000
   ```

   В dev `next.config.ts` проксирует `/api/v1/*`, `/api/admin/*` и
   `/api/health` на backend. `/api/revalidate` обрабатывает сам Next.js.

Начальная конфигурация не содержит учётных данных администратора
и LLM. Заполните нужные значения в локальном env; копии env-шаблонов
сами по себе эти подключения не включают. Формы, модель и реклама
настраиваются независимо.

Для локальной админки задать в `backend/.env.dev` собственные `ADMIN_USERNAME`
и `ADMIN_PASSWORD`, `ADMIN_ALLOWED_ORIGINS=["http://localhost:3000"]`,
`ADMIN_COOKIE_SECURE=false`, затем пересоздать backend командой
`docker compose -f docker-compose.dev.yml up -d --force-recreate backend`. Если открываете сайт через
`127.0.0.1`, добавить этот origin в массив. Войти на `/admin/login`.
Production-шаблоны используют `http://bks-lab.ru`; Origin текущего IP
сохранён для входа на время перехода. При HTTP используется
`ADMIN_COOKIE_SECURE=false`; после подключения HTTPS установить `true`
и согласовать Origin с URL сайта. Приватные env-файлы не обновляются через
Git: параметры и команды перехода — в [инструкции развёртывания](docs/deployment.md#переход-работающего-стенда-с-ip-на-домен-http).
Админка показывает статистику, материалы, подписчиков и обращения; публикации
создаются и редактируются в редакторе `/admin/content` (хранилище —
PostgreSQL, история версий сохраняется). Редакционный центр `/admin/news`
отдельно управляет источниками, анализом и решениями по найденным
материалам. Пустые учётные данные отключают вход.

Форма «Связаться» сохраняет имя, email для ответа и текст обращения в
PostgreSQL. Обращения доступны владельцу в `/admin/feedback`, начиная с
самых новых; ответы выполняются вручную. Успех возвращается после записи
в БД. Подписка сохраняется в PostgreSQL; автоматическая рассылка не включена.

В production публичные запросы идут через nginx, который перезаписывает
`X-Real-IP` и `X-Forwarded-For` адресом посетителя. Backend использует
`X-Real-IP` для статистики и лимитов запросов; его порт наружу не публикуется.
Сеть и адреса контейнеров назначает Docker. При прямом подключении в dev
без `X-Real-IP` используется адрес непосредственного соединения.

## News Analyzer

После запуска backend автоматически применяются миграции и выполняется
`scripts.seed_news`, затем стартует `news-analyzer-scheduler`. Он использует
тот же образ и PostgreSQL, работает без открытой админки и не публикует
HTTP-порт. Seed синхронизирует проверенные источники из кода, темы и рубрики.
Новые источники выключены. Повторный запуск обновляет описания и правила
сбора, сохраняя включение, личное расписание, слаги и историю. При отсутствии
изменений seed ничего не записывает. Повторный запуск вручную:

```bash
docker compose -f docker-compose.dev.yml exec backend python -m scripts.seed_news
```

При локальном backend без Docker выполните `python -m scripts.seed_news`
из каталога `backend` после миграций. Проверенные профили находятся в
`backend/src/news_sources/`; админка получает список из PostgreSQL.
`backend/src/data/news_source_catalogue.json` остаётся исследовательским
списком кандидатов и не определяет доступные в админке источники.

При работе без backend-контейнеров запустите из `backend` также отдельный
процесс `python -m src.background_tasks.news_scheduler` с той же env-
конфигурацией PostgreSQL. Одного HTTP-сервера недостаточно для обработки
фоновой очереди.

Параметры модели задаются только в игнорируемом `backend/.env.dev`:
`NEWS_LLM_PROVIDER`, `NEWS_LLM_API_URL`, `NEWS_LLM_API_KEY` и `NEWS_LLM_MODEL`.
Используется минимально адаптированный клиент из референса
`vera_rag_service/LLM_CLIENT_REFERENCE.md`. Текущая локальная конфигурация —
Polza; модель меняется одной строкой:

```dotenv
NEWS_LLM_MODEL=qwen/qwen3-30b-a3b-instruct-2507
```

После изменения env пересоздайте оба процесса:

```bash
docker compose -f docker-compose.dev.yml up -d --force-recreate backend news-analyzer-scheduler
```

Ключ не передаётся фронтенду; в настройках видны только наличие конфигурации,
провайдер и модель. Без настроенной LLM материалы сохраняются в ожидании
анализа. Учёт расходов и денежные лимиты не реализованы.

Рабочий сценарий:

1. Откройте «Источники» (`/admin/news/sources`): компактная таблица проверенных
   сайтов с названием, кратким описанием и переключателем регулярных проверок.
2. Нажмите на расписание, чтобы настроить его в модальном окне: ежедневно в выбранное время,
   раз в несколько дней от выбранной даты или по дням недели. Время —
   Самара (UTC+4). Включите источник; рядом появится следующая проверка.
3. Нажмите «Проверить» в строке либо «Проверить все включённые» над таблицей.
   Там же виден общий прогресс сбора и отдельно анализа; строки показывают
   очередь, текущую проверку, результат и ошибки. Состояние восстанавливается
   после обновления страницы. «История проверок» открывает все обходы. Ручной сбор
   также доступен в «Запусках». Плановый сбор использует индивидуальное
   расписание. Общая пауза, политика, веса и сроки хранения изменяются
   в `/admin/news/settings`.
4. В подборках «Для статей» и «Короткие новости» просмотрите оценки и
   первоисточник, затем выберите «В работу», «Отложить» или «Отклонить».
   Ожидающие анализа материалы доступны во вкладке «Все материалы».

Добавление сайта выполняется в коде: профиль задаёт адрес, правила разбора
RSS/Atom или HTML и рекомендуемое расписание. Перед включением в реестр
проверяются список публикаций, текст и повторный сбор. В админке нет форм
URL, CSS-селекторов или выбора парсера. Неподдержанные сайты, API и
справочные ресурсы остаются в исследовательском списке.

Автоматические заметки управляются в `/admin/news/notes`: включение,
интервал, срок актуальности, очередь, правка и исключение записи.
Модель готовит заголовок и текст тем же запросом, которым анализирует новость;
ссылка «Подробнее…» берётся из первоисточника сервером. Текст ограничен
300 символами, заголовок — 90. Ручные черновики не входят в эту очередь.
Стартовые значения — одна публикация минимум раз в 10 минут и актуальность
72 часа. После простоя публикации не выходят пачкой, повторный анализ
не создаёт дублей. Режим охватывает новые материалы после первого включения.

На главной — компактная прокручиваемая лента; `/notes` содержит полный архив.
Новые записи появляются по кнопке уведомления, старые подгружаются порциями.
Серверный HTML и ссылки архива остаются доступны без JavaScript.

Аннотация ограничена 500 символами, комментарий модели — 600. Редактор
проверяет первоисточник и принимает решение самостоятельно. «Повторить
анализ» обновляет результат для текущей модели и политики; простая смена
настроек не пересчитывает уже разобранный архив. Правила истории,
восстановления заданий и хранения описаны в [инструкции News Analyzer](docs/news_analyzer.md).

Ручной сбор и повторный анализ возвращают задание сразу;
его состояние доступно по ссылке `/admin/news/jobs/{job_slug}`. По умолчанию первый
обход ограничен 30 днями и 50 материалами на источник, фрагмент для модели —
3000 символами, пакет анализа — 20 материалами. Настройки ограничивают объём
работы, сохраняя собранные материалы при сбое модели. Автопубликации и
изменения Markdown из редакционного центра нет.

В production используйте `NEWS_*` из `.env.production.example` и команды
Compose из [инструкции развёртывания](docs/deployment.md). Оба процесса
должны получать одну конфигурацию LLM; секреты не коммитятся.

## Тесты и проверки

Каждый блок запускается из корня репозитория. Для backend используйте
отдельное Python-окружение. Пример для PowerShell:

```powershell
python -m venv backend/.venv
backend/.venv/Scripts/python.exe -m pip install -r backend/requirements-dev.txt
backend/.venv/Scripts/python.exe -m pytest backend/tests
```

На Linux/macOS путь к интерпретатору — `backend/.venv/bin/python`.
Frontend:

```bash
cd frontend
npm ci
npm run lint
npx tsc --noEmit
npx vitest run
npm run build -- --webpack
npm audit --omit=dev
```

Backend-тестам нужен работающий Docker: `testcontainers` запускает отдельный
PostgreSQL 16. Недоступная БД считается ошибкой проверки; подмены SQLite нет.

Срез после внедрения редактора контента (хранение в PostgreSQL, ревизии,
изображения, рекламный маркер): backend — 512 passed, frontend —
246 passed (Vitest), TypeScript и ESLint чисто. Ручная интеграционная
приёмка редактора (создание → правка → публикация → откат → удаление)
не проводилась.

Проверенный срез от 08.10.2026 (до редактора):

| Проверка | Результат |

| Frontend | 189 passed; TypeScript и ESLint passed |

## Контент

Контент (статьи, заметки, проекты) хранится в PostgreSQL и редактируется
через админку (`/admin/content`): тело — Markdown, при сохранении пишется
версия, обложки и изображения загружаются в `uploads/`. Формат полей —
`docs/content_format.md`, устройство редактора — `docs/content_editor.md`.
Все новые публикации создаются только в редакторе админки. Файлы
`backend/content/` — исторический архив, приложение их не читает.
Production запускается с пустой БД: локальные публикации и uploads не
переносятся, Markdown-файлы не импортируются.

Источники новостей, результаты анализа и решения редактора хранятся
в PostgreSQL отдельно от опубликованного контента. Редакционный центр
не создаёт статьи автоматически и не меняет публикации.

После сохранения материала backend сам вызывает revalidate-webhook
фронтенда: Next.js обновляет кэш без пересборки; при недоступности webhook
кэш истечёт по ISR (5 минут). Первоначальный запуск — в
[инструкции развёртывания](docs/deployment.md).
